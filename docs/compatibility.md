Reference: Papa Parse 5.7.1 (npm `papaparse@5.7.1`, integrity
`sha512-qOR+UDWv6D3hMxnWWOk0ZpBdCkd+kw5Yh7aXOaNSQU8A+73EA2bhW7EiUix/hY0yulUi5FRvt7PpYSI2VDvY0g==`,
git tag `5.7.1` = `af9cc5f41d4bb5307f06bbf1380216bf18651b49`; the npm `papaparse.js` is byte-identical
to the tagged source). Some measurements below were made on Papa Parse 5.7.0 (integrity
`sha512-qBGxg/7Q3Kl9Wfhrz2Z74UnvnHTXLNG6jmKJFeBvP2+y4lV7So+7SR62+Zd47JvdrCkX+nDcnr0ObPzek/+6RA==`,
git tag `5.7.0` = `555c1c1b6175e7a043adf8694983776a1e6fdeeb`); a sentence below that names 5.7.0
was not checked against 5.7.1.

Every R01-R13 row below is implemented in the main entry and in `/papa`, with the exceptions listed
below.
"Reference behavior" is what the pinned Papa Parse does, recorded by executable probes.

Both entries match the reference on everything `test/compatibility.test.ts` compares for them: the 48
fixtures of `test/fixtures/groups.ts`, the upstream parse inputs (main entry 158 compared, 3 rejected values asserted,
7 excluded by name; `/papa` 161 compared), CSV Spectrum, the seeded fuzz with 0-3 combined overlays,
an offline run of 1,008,000 inputs per entry and 1,005,000 unparse inputs per entry, except the
exceptions below (D2-a..l, D3, D4-a, P3-a..c). Papa's own "Parse Tests" and "Unparse
Tests" also run against `/papa` with their own assertions. Two reference algorithms take quadratic
time on adversarial input; csvloom produces the same output in linear time (see "Performance
differences" below).
Rows marked _exception_ are resolved by the exceptions in "Compatibility exceptions" below.

  `csvloom/papa` with their own assertions: 100 and 64 tests, all passing. Four suites and one test

- `test/papa-deviations.test.ts`: named golden tests for the D2 and D3 exceptions, for the reference

## Exclusions

Not in csvloom: jQuery integration, HTTP download and request options, internal and
streamer classes as public API, mutable global settings and `NODE_STREAM_INPUT`, Papa-call
compatibility for `step`, `chunk`, `complete`, `error`, `beforeFirstChunk`, `worker` and `encoding`,
the `parse(File)` and `parse(URL, {download: true})` overloads, legacy polyfills and AMD/UMD/jQuery
builds, and XLSX/database/SQL/UI/plugin features and a schema language of its own. An excluded
option that is requested throws `UnsupportedFeatureError` (D3 below). Row validation through a
caller-supplied Standard Schema v1 object is in scope (F5 in "Features" below); csvloom defines no
schema syntax and ships no validator.

## Features

Every row is implemented. The stream's rows are in "`parseStream` and the features" below, and its
differences from bulk, S8-S11, in the table of "`/stream`". Usage and limits: `docs/features.md`
and `docs/streaming.md`.

What the features leave unchanged:

- `parse`: its signature, overloads, declared types, accepted keys, results and run-time path.
  Each feature key throws `TypeError: Unknown parse option "<key>"` (R11 stays pinned).
- `csvloom/papa`: the same results, errors, seven frozen members and types; it ignores the
  feature keys as it ignores every unknown key, and its `unparse` default stays "no formula
  escaping". Its types are compared with frozen copies, in both directions ("`csvloom/papa` and
  TypeScript" below).
- No new subpath: the new exports are on the package root (`parseDetailed`, `detect`,
  `formatError`, `excel`, `excelSemicolon` and their types).
- D3 `encoding` is unchanged: `detect` reports what bytes look like; nothing but UTF-8 is decoded.
- Excel: no XLSX reading or writing. F4 is CSV text for spreadsheet programs (BOM, `sep=`, `;`).
- Repair is narrow: of stray quotes only a quoted field that never closes is repaired, and a row with a non-empty extra field
  is not repaired (F3-a).

## BOM handling

Papa 5.7.0 strips a leading BOM from string input. It also strips a U+FEFF at the start of every
header cell, not only the first: `a,\ufeffb` with `header: true` gives fields `['a', 'b']`. A U+FEFF
at the start of a data cell is kept.

Both entries do the same: one leading BOM of the input is removed, and with `header` one leading
U+FEFF of each header cell is removed before `transformHeader` runs; every other U+FEFF is data. The
benchmark lanes follow the same rule. The differential tests compare such inputs with headers.

## `/stream`

`parseStream` from `csvloom/stream`; guide `docs/streaming.md`. For a source that ends normally, its batches, concatenated, equal `parse` of the whole text with the same config (rows by strict deep equality and record key order, errors grouped as `Quotes`, `Delimiter`, `FieldMismatch`, and the last batch's `meta` without `rowOffset` and `done`), wherever the chunks split and whatever the source kind, except as S1-S7 say. S8-S11 are the differences of a stream with a feature key from bulk `parseDetailed`; they apply only with the key each row names. Evidence: every split of the seeded fuzz inputs under every overlay (`test/batches.test.ts`, `test/stream-equality.test.ts`) and a long fuzz of 108,000 inputs through the public API with no difference. Every batch but the last holds `batchSize` rows, or fewer, at least one, when the text read for it reaches 1,048,576 UTF-16 units first (`docs/streaming.md`, "The batch"); this changes where batches end, not what they hold together (`test/batches.test.ts`, "BatchBuilder, the bound on a batch’s text").
